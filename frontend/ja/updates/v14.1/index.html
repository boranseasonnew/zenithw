Railway から AWS: ZenithW は独自のサーバーで実行されるようになりました

スクロールして何が変更されたかを確認してください

v14.1 では、ZenithW バックエンドが Railway からアマゾン ウェブ サービス上の独自の EC2 サーバーに移動しました。ドメインとインターフェイスは引き続き Cloudflare の高速エッジ経由で到着しますが、ダウンロード、変換、ライブ進行は専用の Ubuntu ホストで実行されるようになりました。

これはホスティングプロバイダーの名前を変更するだけではありません。ランタイム、ネットワーク境界、サービス監視、および可観測性レイヤーが再構築されました。私たちは、Railway の利便性の一部を残しながら、AWS の制御を取得しました。そして、それに伴う新たな責任については正直に思っています。

以前のRailwayはどうでしたか？

Railway を使用すると、GitHub からデプロイし、アプリ プロセスを監視し、ほとんどのインフラストラクチャ作業を非表示にすることが非常に便利になりました。迅速なセットアップと低メンテナンスは、小規模なチームにとって大きな利点でした。トレードオフとして、オペレーティング システム、ネットワーク、永続的なサービス、およびリソースの使用に対する直接的な制御が低下しました。調査は主に、プラットフォームによって公開されたビューに限定されていました。

AWS では現在何が動作していますか?

バックエンドは現在、Amazon EC2 の t3.small Ubuntu サーバーで実行されています。 Gunicorn と gevent は安全なシングルワーカー アーキテクチャを維持し、systemd がアプリを監視し、Nginx が HTTPS および WebSocket トラフィックを転送します。 FFmpeg とサポート サービスは、明示的なリソース制限付きで同じホスト上で実行されます。

ドアにCloudflare、エンジンルームにAWS

Cloudflare ページは引き続きインターフェイスを提供しますが、DNS、プロキシ、およびパブリック HTTPS は Cloudflare エッジに留まります。 Cloudflare から EC2 への接続は、完全 (厳密) TLS で検証されます。 Nginx は、信頼できるプロキシ チェーン経由でのみ実際の訪問者 IP を受け入れるため、レート制限はスプーフィング可能なヘッダーではなく実際のユーザーに従います。

AWS が私たちに与えてくれるもの

サーバー プロセス、ディスク、メモリ、ネットワーク、サービス ログが直接表示されるようになりました。 Nginx、systemd、ファイアウォール ルール、サポート サービス、およびランタイム制限は、ワークロードに合わせて調整できます。専用の仮想マシンは抽象的なコンテナーのライフサイクルへの依存が少ないため、診断とパフォーマンスのチューニングがより測定しやすくなります。

正直なところ: AWS の欠点

そのコントロールは無料ではありません。オペレーティング システムの更新、セキュリティ パッチ、ディスクの監視、サービスの再起動、証明書、ネットワーク構成は現在、私たちの責任です。単一の EC2 インスタンスは高可用性ではありません。ホストまたはリージョンに問題がある場合、自動の 2 番目のサーバーはまだありません。また、サーバーには静かな期間であってもランニングコストが固定されており、スケーリングには Railway よりも綿密な計画が必要です。

それにしてもなぜ移動するのでしょうか？

ZenithW のメディア ワークロードは、有効期間の長い接続、FFmpeg、WebSocket、および制御された一時ストレージに依存しています。このワークロードでは、Linux ホストを確認し、その制限を直接管理することがより価値のあるものになりました。 Railway が悪いため移動しませんでした。 ZenithW がより高度なインフラストラクチャ制御の恩恵を受けられるようになったため、私たちは移行しました。

つまり、v14.1 は、ZenithW を管理されたプラットフォームの利便性から独自のサーバーの制御に移行します。私たちは、メンテナンス、コスト、可用性の責任を負いながら、可視性と自由を獲得しました。
