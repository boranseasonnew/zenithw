从 Railway 到 AWS：ZenithW 现在在自己的服务器上运行

滚动查看发生了什么变化

在 v14.1 中，ZenithW 后端从 Railway 迁移到 Amazon Web Services 上自己的 EC2 服务器。域和界面仍然通过 Cloudflare 的快速边缘到达，而下载、转换和实时进度现在在专用的 Ubuntu 主机上运行。

这不仅仅是更改托管提供商的名称。重建了运行时、网络边界、服务监管和可观察层。我们获得了 AWS 的控制权，同时保留了 Railway 的一些便利性，而且我们对随之而来的新责任很诚实。

Railway以前是什么样的？

Railway 使得从 GitHub 进行部署、监督应用程序进程并隐藏大多数基础设施工作变得非常方便。快速设置和低维护成本对于小团队来说是真正的优势。权衡是减少对操作系统、网络、持久服务和资源使用的直接控制；调查很大程度上仅限于平台曝光的观点。

AWS 现在运行什么？

后端现在在 Amazon EC2 中的 t3.small Ubuntu 服务器上运行。 Gunicorn 和 gevent 保留了安全的单工作架构，systemd 监督应用程序，Nginx 转发 HTTPS 和 WebSocket 流量。 FFmpeg 和支持服务在同一主机上运行，​​具有明确的资源限制。

Cloudflare在门口，AWS在机舱

Cloudflare 页面继续为该接口提供服务，而 DNS、代理和公共 HTTPS 仍处于 Cloudflare 边缘。从 Cloudflare 到 EC2 的连接通过完全（严格）TLS 进行验证。 Nginx 仅通过受信任的代理链接受真实的访问者 IP，因此速率限制遵循实际用户而不是欺骗标头。

AWS 给我们带来了什么

服务器进程、磁盘、内存、网络和服务日志现在直接可见。 Nginx、systemd、防火墙规则、支持服务和运行时限制可以针对工作负载进行调整。专用虚拟机较少依赖于抽象容器生命周期，从而使诊断和性能调整更加可衡量。

诚实的部分：AWS 缺点

这种控制不是免费的。操作系统更新、安全补丁、磁盘监控、服务重启、证书和网络配置现在都是我们的责任。单个EC2实例不高可用；如果主机或区域出现问题，还没有自动第二个服务器。即使在安静时期，服务器也有固定的运行成本，并且扩展需要比 Railway 上更多的规划。

为什么还要搬家呢？

ZenithW 的媒体工作负载依赖于长期连接、FFmpeg、WebSocket 和受控临时存储。对于此工作负载，查看我们的 Linux 主机并直接管理其限制变得更有价值。我们没有动，因为Railway坏了；我们搬家是因为 ZenithW 现在受益于更深入的基础设施控制。

简而言之，v14.1 将 ZenithW 从托管平台的便利性转移到了其自己的服务器的控制。我们在承担维护、成本和可用性责任的同时获得了可见性和自由。
